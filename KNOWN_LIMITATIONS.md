# Known Limitations

## Live verification outstanding (no credentials in this environment)
- **Supabase**: The migration (`supabase/migrations/20261114000000_orbit_core.sql`) has not been applied to a live database. Local `supabase start` was attempted, but the OS killed it for low memory. RLS policies are therefore untested against a real Postgres.
- **AI provider (Gemini free tier)**: On 2026-11-14, voice analysis, URL discovery, the research report, LinkedIn and X generation, and Guardian each ran live once on `gemini-3.5-flash`, all with schema-valid output (see BUILD_PROGRESS.md). That is one sample per prompt, so quality across many topics has not been measured. RSS discovery, AI rewrite and adaptation, perspective questions and preference analysis haven't run live yet.
- **Buffer**: The personal-API-key path is verified live: `account`, `channels`, `posts`, and `createPost` in draft mode, plus idempotent re-submission. OAuth (Authorization Code + PKCE) was verified live on production on 2026-11-14: consent, callback, token exchange, and channel and post retrieval all worked. Not yet run live: queue and custom scheduling, and the error paths of real `createPost` calls.
- **Deepgram**: Transcription is untested live.
- **End-to-end tests**: `npm run test:e2e` (Playwright) covers the demo path from sign-in to the Buffer final confirmation, with Gemini and Buffer mocked inside the test server (`tests/e2e/mocks/preload.mjs`). It never clicks Approve. Supabase is real: each run creates a throwaway `orbit-e2e-*@example.com` user and deletes it afterwards. Live Buffer sends were verified separately by hand (2026-11-19, all test drafts deleted).
- **RSS discovery with Gemini free tier** (2026-11-19): following a feed and fetching/parsing it work live, but the analysis call for 20 feed items timed out twice (2 × 120 s) and the UI showed "The AI provider is temporarily unavailable. Your saved work is safe." Not retried, to save free-tier quota. Large feed batches may need a smaller item cap or a background job.

## Product limitations
- **No web search discovery**: With the Gemini provider, Radar's "Web search" tab returns a clear "web search unavailable" message. Discovery works from submitted URLs and RSS/Atom feeds only. Radar opens on "From URLs", and the Web search tab explains that it is unavailable instead of offering a button.
- **Free-tier quotas**: Gemini free-tier requests are rate-limited per minute and per day, and they surface as "rate limit or free-tier quota reached". Google's free-tier terms allow submitted content to be used to improve their products, so do not process confidential material on the free tier.
- **Model availability**: Google retires model aliases for new users (e.g. `gemini-2.5-flash`). If the default stops working, set `GEMINI_MODEL`.
- **Media**: Drafts can carry up to 10 JPEG/PNG/GIF images (4 MB each), sent to Buffer as image assets with alt text (TD-021). Verified live on LinkedIn drafts. No video, no image editing or cropping, no image generation (Studio still offers a labelled *visual brief*). Per-platform limits come from platform documentation, not from Buffer's API. **Instagram** is enabled when an image is attached but has not been tested live (no Instagram channel connected). Images sent to Buffer use 365-day signed URLs; a post scheduled further out would lose its image. Deleting a draft deletes its image files, except images already sent to Buffer: those files are kept so scheduled posts can still fetch them, and there is no automatic cleanup of them yet.
- **Threads**: X threads go to Buffer as `metadata.twitter.thread` with every part (top-level `text` is part 1), following the live schema introspected on 2026-11-14 (`TwitterPostMetadataInput.thread: [ThreadedPostInput!]`). This is unit-tested, but no live thread post has been created yet. On non-X channels only the first part is sent. The ledger's `text_sent` records part 1, the text Buffer stores at top level.
- **Content Items** (Buffer, experimental): "Send variants together" groups a generation's variants into one `createContentItem` (TD-023), verified live with a LinkedIn + X draft. Because the API is experimental and a failed item may still have created posts, a failed grouped send is recorded as `unknown` per post. The standard publish dialog still sends one `createPost` per channel.
- **Editing or deleting Buffer posts** is not implemented. Changing a campaign date changes only ORBIT's plan.
- **Analytics**: The Performance panel on Publishing reads `Post.metrics` for posts ORBIT sent (TD-022). Buffer only grants the required `insightsRead` scope to personal API keys, so OAuth-connected accounts see an explanation instead of numbers. Buffer's free plan only covers about the last 31 days, and metrics appear about a day after a post is sent. The query was verified live; no ORBIT-sent post had been published yet, so no real metric values have been displayed. No manual or CSV import.
- **Context monitoring** (Guardian detecting that scheduled content became outdated) is not implemented. Guardian marks content `stale` after edits, and that is all.
- **Background jobs**: Research runs inside the request, which can take up to about 60 s. There is no job queue or scheduled Radar scans; feeds are scanned on demand.
- **Rate limiting**: Only provider limits apply. There is no application-level rate limiting.
- **Platform limits** (`src/engines/studio/platforms.ts`) reflect commonly documented values and should be re-verified against each platform's current documentation.
- **Statistic matching**: Guardian's "number not in sources" check is substring-based, so "40" also matches "1400". It is a hint, not proof.
- **Node 22 required**: on Node 20, the installed `@supabase/supabase-js` throws "native WebSocket not found" as soon as a client is created, so every Supabase call would fail at runtime. `next build` still passes because it renders no pages. `package.json` `engines` and `.nvmrc` now pin Node 22 (`nvm install 22 && nvm use 22`).
- **Single voice profile**: There is one default voice profile per user. There is no multi-brand support.
- **Pre-existing hydration warning**: `/research/:id` logs React error #418 (hydration text mismatch) in the browser console on both production and local builds. The page works; it predates the post-commit branch and was left unchanged.
